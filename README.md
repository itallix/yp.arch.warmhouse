### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Администраторы системы могут добавлять, изменять и удалять датчики температуры, а также управлять их параметрами (название, тип, местоположение, единица измерения, статус).
- Система поддерживает хранение данных о датчиках температуры в базе данных.
- Реализована возможность обновления текущего значения и статуса датчика через API.

**Мониторинг температуры:**

- Пользователи могут просматривать текущие значения температуры в своих домах через веб-интерфейс.
- Система поддерживает интеграцию с внешним API для получения температуры по местоположению или идентификатору датчика.
- Реализована возможность мониторинга всех датчиков и получения из списка с актуальными значениями.

### 2. Анализ архитектуры монолитного приложения

* Язык программирования: `Go`
* База данных: `PostgreSQL`
* Архитектура: `Монолитная`, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
* Взаимодействие: `Синхронное`, запросы обрабатываются последовательно.
* Масштабируемость: `Ограничена`, так как монолит сложно масштабировать по частям.
* Развертывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

#### Домены:
* Домен управления датчиками температуры:
	* Операции по созданию, обновлению, удалению и получению информации о датчиках.
	* Хранение и обработка метаданных датчиков.
* Домен мониторинга температуры:
	* Получение текущих значений температуры по местоположению или идентификатору датчика.
	* Интеграция с внешним API для получения температуры.

#### Границы контекстов:
* Границы контекстов определяются доменами.
* Контекст управления датчиками ограничен CRUD-операциями и внутренним состоянием датчиков.
* Контекст мониторинга температуры включает интеграцию с внешним API.


### **4. Проблемы монолитного решения**

- Слабая масштабируемость: Все функции реализованы в одном приложении, что затрудняет масштабирование отдельных частей системы (например, мониторинга температуры отдельно от управления датчиками).
- Сложность поддержки и развития: Любые изменения в одной части приложения могут повлиять на другие, что увеличивает риски и время на внедрение новых функций.
- Ограниченная гибкость интеграций: Интеграция с внешними сервисами (например, температурными API) реализована внутри монолита, что усложняет замену или расширение интеграций.
- Сложности с разделением ответственности: Отсутствие четких границ между доменами приводит к смешению бизнес-логики и усложняет выделение отдельных сервисов в будущем.
- Потенциальные проблемы с отказоустойчивостью: Сбой в одной части монолита может привести к недоступности всей системы.

Если вы считаете, что текущее решение не вызывает проблем, аргументируйте свою позицию.

# Задание 4. Создание и документирование API

### 1. Тип API

#### REST API
- CRUD операции - управление устройствами, пользователями, сценариями
- Запросы данных - получение состояния устройств, истории телеметрии
- Команды с ожиданием результата - включение/выключение устройств
- Конфигурирование - настройки пользователей, параметры устройств

#### AsyncAPI
- Телеметрия в реальном времени - данные с датчиков каждые N секунд (N - настраиваемый параметр)
- События устройств - подключение/отключение, ошибки
- Автоматизация - запуск сценариев по триггерам
- Уведомления - алерты безопасности, обслуживания

#### Обоснование выбора
- REST API подходит для CRUD операций и получения данных, так как обеспечивает простоту и предсказуемость взаимодействия.
- AsyncAPI необходим для обработки высокочастотных данных (телеметрия) и событий, что позволяет обеспечить асинхронность и масштабируемость системы.
- Комбинация обоих подходов позволяет гибко управлять устройствами и получать данные в реальном времени, что критично для IoT приложений.

#### Распределение по сервисам
Сервис | REST API | Event-driven | Обоснование 
----- | --------- | ------------- | -------------
Device Management | ✅ Управление устройствами | ✅ События устройств | Конфигурация через REST, статусы через события
Device Communication | ❌                      |✅ Телеметрия, команды | Высокочастотные данные только через Kafka
Automation Service | ✅ CRUD сценариев | ✅ Выполнение автоматизации | Настройка через REST, выполнение через события 
Telemetry Service | ✅ Запросы истории | ✅ Прием данных | Аналитика через REST, прием через Kafka
Notification Service | ✅ Настройки уведомлений| ✅ Обработка алертов | Конфигурация через REST, доставка через события

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

# **Задание 6. Разработка MVP**

Необходимо создать новые микросервисы и обеспечить их интеграции с существующим монолитом для плавного перехода к микросервисной архитектуре. 

### Реализованные компоненты
#### Микросервисы
Разработаны два микросервиса на Node.js:
- `device-management` — сервис для управления устройствами с базовой логикой создания и управления сенсорами.
- `telemetry-api` — сервис для работы с телеметрическими данными, включая сбор, хранение и предоставление метрик устройств.
#### Инфраструктура
Добавлены компоненты для обеспечения работы микросервисов:
- `Apache Kafka` — брокер сообщений для асинхронного взаимодействия между сервисами.
- `InfluxDB` — time-series база данных для хранения телеметрических данных.

### Архитектура взаимодействия
При создании нового сенсора происходит следующий workflow:

1. Сервис device-management создает сенсор и отправляет событие в очередь Kafka
2. Сервис telemetry-api получает уведомление и начинает генерировать случайные измерения с настраиваемым интервалом
3. Данные сохраняются в InfluxDB для последующего получения
4. При запросе телеметрии возвращается последнее сохраненное значение

### API endpoints
В монолит интегрированы следующие API методы:

POST /sensors — создание нового сенсора
GET /sensors/{id} — получение детальной информации о сенсоре по ID
